## M2 迷宫核心数据结构

**目标：** 让 `Cell` / `Maze` 从 `NotImplementedError` 变成可用，且把"墙必须成对出现"
这条不变式收敛到一个地方维护。

**设计决策：**

- `carve(a, b)` 是唯一修改墙的入口：先校验相邻、再同时清两侧的墙位，
  这样"墙位对称"不会因为某处只改一边而被破坏。
- 区分 `adjacent()` 与 `neighbors()`：生成算法遍历时所有墙都还在，
  用 `neighbors()`（只看通路）会得到空列表，所以生成阶段必须用 `adjacent()`（只看边界）。
  这个坑在一次调试中才发现——最初 DFS 的第一帧永远没有候选邻居。
- `to_dict()` 只存 `[[walls]]` 整数矩阵，`from_dict()` 忽略不认识的键，
  因此生成文件里可以附带 `algorithm` / `seed` 元信息，仍然能被 `solve` / `validate` 直接读取。
- 渲染用 `to_ascii()`，`path` 标 `*`，`marks` 可覆盖单格字符（起终点 S/G）。

**验证：** `tests/test_maze.py` 覆盖打通幂等、不相邻报错、越界报错、
1×1 与单行单列、JSON 往返、7 种非法输入。

## M3 校验器与路径工具

**目标：** 把"什么是合法迷宫"写死成可执行判据，避免演示时靠肉眼判断。

**实现：** `core/validate.py` 四项检查——边界封闭、墙位对称、全连通、无环
（无环用"通道数 = 格数 − 1"判定，连通图下两者等价于"是一棵树"）。
`core/path.py` 负责从父指针回溯路径，并对一条路径逐项验合法性（相邻、无墙）。

**验证：** `tests/test_validate.py` 人为构造四类缺陷，确认每一种都能被单独检出；
另外断言校验过程不修改迷宫（`to_dict()` 前后一致）。

## M4 三种生成算法

**统一接口：** 每个模块提供 `generate()`（直接拿迷宫）与 `generate_steps()`（拿逐帧快照）。

**设计决策：** `generate()` 不另写一遍算法，而是消费 `generate_steps()` 的结果。
逻辑只有一份，代价是快照开销；为了保证两者一致，测试里加了"把每一步 `extra["carve"]`
重放到一个空迷宫，结果必须等于 `generate()`"的用例（三种算法各一条）。

**M4.1 DFS 回溯：** 显式栈而不是递归，避免大迷宫触发 Python 递归深度限制；
每步"压栈前进"或"弹栈回溯"都产出一帧。

**M4.2 随机 Prim：** frontier 用最小堆，每条候选边带一个随机权重；
"随机挑一条边"用"随机权重 + 取最小"实现，正好对应课堂上的优先队列。

**M4.3 Kruskal + 并查集：** 把所有相邻格之间的墙当作候选边随机打乱，
用并查集判断两端是否已连通，已连通则丢弃（否则成环）。并查集单独成模块
（`core/disjoint_set.py`），带路径压缩与按大小合并。

**验证：** 三种算法 × 六种尺寸（1×1、1×6、6×1、2×2、3×7、8×8）全部通过四项自检；
同 seed 完全复现，5 个不同 seed 产生 5 种不同迷宫。

**实测（12×12，5 个种子平均）：**

| 算法    | 平均死路数 | 平均最短路径 |
| ------- | ---------- | ------------ |
| DFS     | 16.2       | 49.6         |
| Prim    | 43.8       | 28.8         |
| Kruskal | 42.8       | 28.4         |

结论：DFS 的迷宫走廊长、死路少（解路径几乎两倍于 Prim/Kruskal），
Prim 与 Kruskal 的形态接近。这组数字是"为什么选 DFS 做长路径迷宫"的直接依据。

## M5 求解算法

**BFS：** 队列 + 父指针，首次发现终点即返回（BFS 逐层推进，首次发现的层数就是最短路）。
**A\*：** 优先队列按 f = g + h 取最小，h 用曼哈顿距离；同一格可能被多次压堆，
弹出时用 `closed` 跳过过期条目，保证每格只扩展一次。

**验证：** 路径逐项合法性、BFS 与 A\* 在 3 种生成算法 × 10×10 迷宫上长度一致、
无解返回 `None`、起终点重合返回单点路径、越界报错。

### 一次被测试推翻的假设

最初写的断言是「开阔网格上 A\* 扩展的格子数 ≤ BFS」。跑测试直接失败：`9 <= 7` 不成立。
查下来原因是 3×3 开阔网格里每格的 f = g + h 都等于最短距离 4，f 值全部并列，
A\* 只能按平局顺序推进，于是把 9 格全扩展了；BFS 反而在发现终点时就停了。

进一步实测完美迷宫（8/10/14 三种尺寸，各 5 个种子），A\*/BFS 扩展比在 0.72–1.02 之间，
有 3 次 A\* 还略多。所以：

- 断言改成两条**真正成立**的：开阔网格上 A\* 确实扩展全区（把已知行为固定下来）、
  A\* 永不重复扩展同一格；
- README 里不写"A\* 一定更快"，只写"路径长度与 BFS 一致，扩展数在走廊型迷宫上接近"。

这条记录保留下来，是因为它正好说明"测出来的结论"和"看起来合理的结论"经常不是一回事。

> 后续：M9 用平局策略把这个问题真正修掉了。"扩展全区"不再是已知行为，
> 对应断言也改成了"A\* 在开阔 3×3 上只扩展 5 格"。

## M6 命令行

**实现：** `generate` / `solve` / `validate` 三个子命令，核心逻辑仍留在库函数里，
CLI 只做参数解析与输出。`main(argv=None)` 可被测试直接调用，返回退出码：

并覆盖损坏 JSON、非法坐标、未知算法、缺参数。

拆成上百行），实现方式是 dump 之后把两元素整数数组重新折行。

## M8 测试阶段修正的两处错误（都在用例里，不在实现里）

这一节专门记录"跑测试时发现不对劲"的两个时刻。两处的共同点是：
**第一反应都以为是实现有 bug，查下来发现是用例本身写错了。**
把它们单独记下来，是因为"判断错误出在哪一层"比"把测试改成绿的"重要得多。

### M8.1 A\* 的扩展数断言方向反了

- **原断言：** 开阔 3×3 网格上，`A* 扩展格数 ≤ BFS 扩展格数`。
- **实际结果：** `assert 9 <= 7` 失败——A\* 扩展了 9 格，BFS 只扩展 7 格。
- **为什么不是实现 bug：** 3×3 开阔网格里，每格的 `f = g + h` 都恰好等于最短距离 4，
  整片区域 f 值完全并列。A\* 按平局顺序推进，于是把 9 格全部扩展；
  BFS 则在"发现终点"那一步就停了。这是 A\* 在启发式失效区域的**固有行为**，不是错误。
- **扩大到实测：** 8×8 / 10×10 / 14×14 各 5 个种子，A\*/BFS 扩展比在 0.72–1.02 之间，
  有 4 次 A\* 反而更多。所以"A\* 一定更快"这个直觉在走廊型迷宫上根本不成立。
- **修正：** 换成两条真正成立的性质——开阔网格上 A\* 确实扩展全区（把已知行为钉死）、
  A\* 永不重复扩展同一格。
- **源码改动：** `solvers/astar.py` 一行未改。

### M8.2 边界检查用例的构造起点错了

- **原用例：** `maze = Maze(3, 3)`，然后清掉 `(0, 0)` 的北墙，期望只有"边界封闭"失败。
- **实际结果：** 连通性与无环也一起失败了。
- **为什么不是生成器漏洞：** `Maze(3,3)` 是刚构造的空迷宫，**一条通道都没有**，
  9 个格子互相孤立，通道数 0 ≠ 格数−1，本来就不可能通过连通性和无环检查。
  是"用例拿了个非法迷宫当基线"，不是生成算法把边界打通了。
- **修正：** 先用 `generate("dfs", 3, 3, seed=1)` 拿一个合法迷宫，再在最外圈开洞，
  这样失败集合才精确等于 `{"边界封闭"}`。
- **源码改动：** `core/validate.py`、三个生成器均一行未改。

### 怎么快速核实这两条

```powershell
git show cfee123 --stat            # 该提交只动了 tests/，没有源码文件
git show cfee123 -- tests/         # 可以看到断言是怎么改的
git log --oneline -- src/mazelab/solvers/astar.py src/mazelab/core/validate.py
```

如果真是实现 bug，修正它的提交里必然有对应源码的 diff；这两处没有，就是最直接的证据。

## M9 性能与算法优化：两个被实测数据揪出来的问题

M5 留下了一句"A\* 扩展数不比 BFS 少"的记录。这次不满足于"记录下来"，改成真正修。
动手前先测了基线，结果比预想的严重。

### M9.1 生成器：`generate()` 一直在为不需要的快照付钱

**基线（70×70，单次生成）：** DFS 590 ms、Prim **30,870 ms**、Kruskal 83 ms。

**原因：** 三个 `generate()` 都靠消费 `generate_steps()` 实现，而每一帧快照都要
`set(visited)` 复制一份已访问集合，Prim 还额外复制整个堆与 frontier 列表。
每帧 O(n)，全部走完就是 O(n²)。70×70 有 4900 格，Prim 的堆又比格子数更大，
于是 30 秒都花在"构造没人看的快照"上。

**改法：** 给三个 `generate_steps()` 加 `capture=True` 关键字参数，
`capture=False` 时不构造任何快照、只推进算法状态；`generate()` 传 `capture=False`。
另外 Prim 的 frontier 改成增量维护的 `set`（入堆时加、访问时丢），
不再每帧重新扫描整个堆。

**改后：** DFS 122 ms、Prim 120 ms、Kruskal 111 ms。Prim 提速约 257 倍。

### M9.2 A\*：平局策略换掉之后，开阔区不再被扫光

**基线：** 开阔 10×10 上 A\* 扩展 100 格（= 全部格子），开阔 3×3 上扩展 9 格。
原因是所有格子的 f = g + h 都相等，堆里只能按入堆顺序弹出。

**改法：** 堆元素从 `(f, 入堆序号, 坐标)` 改成 `(f, -g, 坐标)`。
f 相同时 `-g` 更小（g 更大）的先出，也就是优先走更深的节点、更快逼近终点。
这不影响正确性——f 相同说明都在同一条最优代价线上——只是换了个更聪明的走法。

**改后：** 开阔 10×10 从 100 → **19** 格，3×3 从 9 → **5** 格（同场景 BFS 分别为 98、7 格）。

**完美迷宫上的补充实测**（8×8 / 10×10 / 14×14，各 5 个种子）：

|         | 修复前 | 修复后 |
| ------- | ------ | ------ |
| 合计扩展比 A\*/BFS | 0.923 | 0.899 |
| 比值区间 | 0.72–1.02 | 0.64–1.02 |
| 比 BFS 多的种子数 | 3 | 2 |

结论要说准：**A\* 在开阔场景有明显优势，在走廊型迷宫里只是"通常略省"，并非总是更省。**
仍有 2 个种子 A\* 多扩展了 1–2 格，这是启发式信息不足导致的，不是 bug。

### 测试也随之改了

原来那条 `test_astar_expands_the_whole_plateau_on_open_grid` 断言"扩展全部 9 格"，
是把当时的缺陷固定成了预期。现在改成 `test_astar_tie_break_beats_bfs_on_open_grid`，
断言"恰好 5 格，且少于 BFS、少于总格数"——既记录新行为，也防止以后退化回扫全区。

### 反思

这两个问题都不是"写错了"，而是"能跑、结果也对，但代价不合理"。
没有基线测量就发现不了；而基线测量只花了十几行脚本。
所以 M6 里提到的"缺自动化 benchmark"确实是个真缺口，下一步该补。
